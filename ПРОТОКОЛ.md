# ПРОТОКОЛ ПРОГРАММИРОВАНИЯ — PlannerAI

## 1. Цель создания

Протокол — единый журнал работы над проектом **PlannerAI** (планировщик производства труб,
участок ТБТ). Он существует, чтобы:

1. **Сохранять контекст между сессиями.** Каждая новая сессия Алисы начинается «с чистого
   листа»: без этого файла заново приходится анализировать весь проект и рисковать
   сделать то, что уже сделано, или сломать то, что починено.
2. **Фиксировать не только «что сделано», но и «почему».** Решения, гипотезы, спорные
   места — всё, что потеряется без записи.
3. **Давать быстрый вход в работу.** По протоколу видно состояние проекта на текущий
   момент: что готово, что в работе, что только обнаружено.
4. **Служить единственным источником истины.** Если текст протокола и память расходятся —
   истина в протоколе.

## 2. Инструкция для Алисы (как работать с протоколом)

Этот раздел — прямое указание Алисе при каждой сессии:

1. **Начало сессии.** Прочитать протокол ЦЕЛИКОМ перед любыми действиями. Если протокол
   не приложен к сообщению — попросить пользователя его прислать (файл лежит в корне
   проекта: `ПРОТОКОЛ.md`).
2. **Проверка окружения.** Сверить, что структура проекта на диске совпадает с разделом 5.
   Если нет — внести поправку в протокол.
3. **Любое изменение кода** сопровождать записью в раздел 6 (Журнал): дата, суть,
   затронутые файлы, статус. Формат записи — см. раздел 3.
4. **Любое новое наблюдение** (баг, слабое место, вопрос пользователя) — в раздел 7
   (Реестр дефектов) с присвоением очередного номера D-xx.
5. **Правило «сначала протокол».** Изменение, противоречащее записи протокола, —
   повод не менять код, а сначала обсудить и обновить протокол.
6. **Не переписывать историю.** Старые записи не удалять и не редактировать задним
   числом. Ошибку исправлять новой записью («отмена D-xx, вместо этого …»).
7. **Формулировки — конкретные.** Не «починил сервис», а «добавлены методы get_kpi,
   get_utilization… в service.py, строки 45–120».
8. **В конце сессии** убедиться, что все изменения сессии отражены, и выдать
   пользователю обновлённый файл протокола.

## 3. Формат записи в журнале (раздел 6)

```
### [YYYY-MM-DD] Краткий заголовок
- **Затронуто:** список файлов
- **Сделано:** что именно изменилось
- **Решения:** почему так, а не иначе (если есть выбор)
- **Статус:** DONE / WIP / PLAN / CANCELLED
```

Порядок записей — новые сверху. Одна запись = один логический шаг, а не вся сессия.

## 4. Формат записи в реестре дефектов (раздел 7)

| Поле | Значение |
|---|---|
| ID | D-1, D-2, … (сквозная нумерация) |
| Описание | Что именно не так и где |
| Серьёзность | КРИТ / ВЫСОКАЯ / СРЕДНЯЯ / НИЗКАЯ |
| Статус | OPEN / WIP / FIXED / WONTFIX |

Дефект закрывается только когда код изменён и проверен.

## 5. Состояние проекта (срез на 2026-11-26)

**Стек:** PySide6 + pyqtgraph, pandas, ortools (CP-SAT), SQLite, YandexGPT
(OpenAI-совместимый API), PyInstaller.

**Назначение:** десктоп-планировщик производства бурильных труб. Загружает выгрузки
1С в Excel, строит расписание (job-shop, CP-SAT), показывает KPI и графики,
управляется текстом через LLM-агента (11 tool-функций).

**Структура:**

```
PlannerAI-main/
├── run.py, config.yaml, build.spec, requirements.txt
├── agent/   llm.py (промпт + цикл tool-calling), tools.py (11 схем), worker.py
├── core/    scheduler.py (CP-SAT), bom.py, routing.py, loader.py, analytics.py, service.py
├── storage/ db.py (SQLite: чат, снапшоты, настройки)
├── ui/      main_window.py, chat_panel.py, dashboard.py, charts.py, style.css
└── данные:  План производства.xlsx, Разузловка.xlsx, Операции по спецификациям.xlsx,
             Сотрудники ноябрь 2026.xlsx, Структура.txt, виды рц.txt
```

**Ключевые факты:**
- Планировщик работает только от «Плана производства» (16 позиций) + фиксированных
  маршрутов из config.yaml; `bom.explode` в коде не вызывается.
- «Операции по спецификациям.xlsx» и «Сотрудники ноябрь 2026.xlsx» не используются
  ни одним модулем.
- 6 из 11 инструментов агента вызывают отсутствующие методы service.py (см. D-1).
